# S7 observed-finding ledger

S7 answers a narrow, reproducible question: what did a Blueprint tool print on a
specified actual-project command? It is not fixture coverage, a product-test
result, or a statistical precision estimate.

## Files and boundary

`s7_ledger.py record` writes three append-only data sets beneath `--out`:

- `executions.jsonl` has exactly one row for every attempted command, including
  its exit/timeout, command, state, scenario and correlation IDs, separate raw
  stdout/stderr paths and hashes, and a headline count. A zero count is an
  observed zero-headline execution; it is not a pass for every semantic check.
- `emissions.jsonl` has one `run_id:seq` row for each actual `⚠` or `✗`
  Blueprint headline. The collector accepts only an argv containing the declared
  `validate_blueprint.py`, `apply_blueprint.py`, or `validate-scaffold.sh`.
  Arbitrary domain-test output cannot become a tool finding.
- `adjudications.jsonl` is written by a person. Its four classifications are
  `actionable`, `informational`, `noise`, and `unknown`. `unknown` is a reasoned
  completed judgement; a missing row is **pending** and invalidates completion.

The stable `tool.check_id` comes from the collector catalog. A headline that has
no narrow catalog match is retained as `unmapped`, counted in reports, and makes
`validate` fail. The collector never drops it to improve a noise number.

Environment stderr, timeouts, and nonzero exits without a matching Blueprint
headline remain in execution raw logs and `nonheadline_failure`; they are not
relabelled as Blueprint findings. Intentional mutations and probes use their own
state and correlation group. Shell variants and repeated feature states share a
correlation ID, so summaries cannot present correlated repetitions as independent
precision samples.

Every execution also names the SHA-256 of all four S7 source files. Their exact
bytes are deduplicated under `source/<sha256>` in the evidence output. Ledger
validation hashes those stored bytes again, so a historical ledger remains
verifiable after its disposable checkout is gone and cannot accept a merely
well-formed forged source SHA.

The schema is versioned (`schema: 1`) in every execution, emission, and human
adjudication row. A completed adjudication includes its reason, adjudicator, and
a safe relative raw-evidence path that exists in the campaign output. A failed
process spawn is retained as exit 127 and a non-headline failure; it is never a
green zero-finding run.

## Recollect an actual project

Use a full-history clone at the exact project revision. Replace only its vendored
extension with the candidate source; do not edit the original R14 project. The
manifest runner accepts portable `PROJECT=/clone` mappings and only replaces an
extension after the explicit `--replace-extension` acknowledgement:

```bash
python3 scripts/python/s7_ledger.py collect --out /tmp/s7-r14 \
  --manifest tests/corpus/s7/r14-actual-campaign.json \
  --project-root novice=/path/to/full-history-novice-clone \
  --project-root senior=/path/to/full-history-senior-clone \
  --project-root guru=/path/to/full-history-guru-clone \
  --extension-root "$PWD" --replace-extension
```

Restore those clones from the tracked bundles and exact heads in
`tests/corpus/s7/projects/PROJECTS.json` before collection. The collector stores
glyph headlines and `ERROR:`/usage diagnostics from a verified Blueprint argv;
other stderr remains raw evidence or a non-headline outcome.

From the repository root, restore all three full-history projects into a fresh
directory, then use these paths in the collection command above:

```bash
mkdir -p /tmp/s7-projects
git clone tests/corpus/s7/projects/project-novice.bundle /tmp/s7-projects/novice
git -C /tmp/s7-projects/novice checkout --detach 1bb97526918b00c834d0fe6a5771c0cc0ecdc344
git clone tests/corpus/s7/projects/project-senior.bundle /tmp/s7-projects/senior
git -C /tmp/s7-projects/senior checkout --detach 751a30839d9741eabdebd476ae9ed05ab7bee4a6
git clone tests/corpus/s7/projects/project-guru.bundle /tmp/s7-projects/guru
git -C /tmp/s7-projects/guru checkout --detach cf57436065292db3c1c5adc0173a7a40a78f129e
```

For a single command, use `record` directly:

```bash
python3 scripts/python/s7_ledger.py record \
  --out /tmp/s7-r14 --run-id guru-complete-b-verify-bash5 \
  --campaign r14-actual-projects-v1 --scenario guru-002-complete-b-verify \
  --correlation guru-002-complete-b-verify --state baseline --tool apply \
  --cwd /path/to/full-history-guru-clone -- \
  python3 .specify/extensions/blueprint/scripts/python/apply_blueprint.py \
  specs/002-transfer-history --verify
```

The command's exit is returned after rows and raw logs are written. A campaign
manifest has an explicit `runs` list; `validate --manifest` rejects an empty
list or a missing/extra run. Run all
declared entries in `tests/corpus/s7/r14-actual-campaign.json`; use project-root remapping
when clones live elsewhere. Record direct project tests and semantic mutation
oracles in separate campaigns, not as tool headlines.

After the reviewer writes one adjudication for every emission:

```bash
python3 scripts/python/s7_ledger.py adjudicate --out /tmp/s7-r14 \
  --emission-id guru-complete-b-verify-bash5:01 --classification actionable \
  --reason 'verification command failed' --adjudicator reviewer-id \
  --evidence raw/guru-complete-b-verify-bash5.stdout
python3 scripts/python/s7_ledger.py validate --out /tmp/s7-r14 \
  --manifest tests/corpus/s7/r14-actual-campaign.json
python3 scripts/python/s7_ledger.py summarize --out /tmp/s7-r14 \
  --manifest tests/corpus/s7/r14-actual-campaign.json
```

`validate` rejects duplicate IDs, unknown run references, raw-log absence or hash
mismatch, raw/emission reparse disagreement, manifest metadata or argv mismatch,
source-snapshot disagreement, headline-count disagreement, unmapped diagnostics,
invalid classes, and pending adjudications. `summarize` reports tool runs, zero-headline runs,
headline runs, headline count, unmapped and pending counts, and correlation-group
count. It intentionally does not invent per-check eligible-run denominators or a
general precision value.

## Retained R14 actual-project sample

`results/r14-actual-projects-v1` retains 60 executions, 48 with no headline and
12 with headlines, producing 14 emissions: 3 actionable, 1 informational, and
10 noise. Tool exits are 58 exit 0, one exit 1, and one exit 3. Warning-only
executions can exit 0; a zero-headline count is also distinct from process success.
Validate has 12 runs (8 zero-headline), apply 18 (16 zero-headline), and scaffold
30 (24 zero-headline). All 14 emissions have reasoned adjudications; no unmapped
or pending records remain.

The 10 noise emissions all concern the senior project's completed Feature A:
its permitted Pre-completed Tasks tables have no task headings or task-header
Requirements fields, and its declared zero new files make a no-NEW warning
inapplicable. The two guru header warnings repeat one arithmetic mismatch
(3 declared modified files versus 4 actual paths); its T003 verification command
omits the CLI arguments and gets the specified usage exit 2. The novice build
outcome remains informational because a stale-stamped build is not evidence of
a Blueprint document defect. Raw logs and individual adjudication reasons retain
these distinctions.

This reuses the exact R14 project heads; it is a retained actual-project sample,
not an independent replication or a general precision measurement. Explicit
correlation groups number 12 for validate, 18 for apply, and 15 for scaffold;
even different groups may share a feature and cause, so these are grouping
metadata, not independent sample counts. The R14 baseline also had 60 matrix
runs, but its old/new change comparison is a different measurement.

`results/r14-actual-projects-v1/provenance-source/s7_ledger.py` preserves the
collector bytes used at collection time. The current `scripts/python/s7_ledger.py`
is the validator with subsequent integrity hardening. The historical collector
snapshot is provenance, not a claim that the latest validator ran during
collection. Validate the retained ledger with the current script and manifest.

`tests/corpus/s7/schema.json`, `adjudication.example.jsonl`, and the campaign manifest
are tracked review artifacts. Large raw actual-project logs may live in the
campaign evidence directory, but their paths and hashes are part of the ledger.
